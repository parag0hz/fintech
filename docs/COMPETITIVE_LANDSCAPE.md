# 경쟁·선행 기술 지형 (Competitive Landscape)

**한 줄 요약** — "AI가 실행 직전에 뭔가 확인한다"는 제품·논문·특허는 이미 많습니다.
이 문서는 그중 **35건을 원문까지 확인해** 정리하고, 우리가 **무엇을 새로 하지 않는지**와
**어디가 남아 있는지**를 구분합니다. "최초"라고 주장하지 않습니다.

조사 방법: 8개 축(국내 증권사 / 국내 음성뱅킹 / 해외 상용 / 가드레일 벤더 / 학계 /
Text-to-SQL 검증 / 특허·표준 / 한국어 NLP)으로 병렬 조사 후, 후보마다 **URL 원문을 다시 열어**
인용문이 실제로 존재하는지 검증했습니다. 후보 40건 전원 실재 확인, 중복 제거 후 35건.
검증 단계에서 겹침 등급이 하향된 항목(직접경쟁 → 인접)은 그대로 표기했습니다.

## 0. 비교 축 — "무엇을 검증하는가"

제품 이름이 아니라 **검증 대상**으로 나눠야 지형이 보입니다.

| 축 | 무엇과 무엇을 대조하는가 | 대표 |
|---|---|---|
| **(a) 보안** | 조직 정책 ↔ 에이전트 행동 | Zenity, Operant AI |
| **(b) 문법** | 스키마 ↔ 생성된 호출 | 함수콜 밸리데이터, SPARC 앞단 |
| **(c) 한도·규정** | 계좌·규정 ↔ 주문 파라미터 | 토스증권 API, 금투협 모범규준 |
| **(d) 의미 일치** | **사용자가 방금 한 말 ↔ 주문 파라미터** | ← **우리 자리** |

국내 금융 실서비스는 거의 전부 **(c) + 사람 눈 확인(echo-back)** 조합입니다.
(d)를 정면으로 다루는 곳은 대부분 **학계**와 **Text-to-SQL** 쪽입니다.

**중요**: 신한 슈퍼SOL은 기사에서 "별도 비밀번호·메모 절차를 최소화, 생체인증만으로 송금 완료 —
금융권에서 가장 짧은 송금 프로세스"라고 소개됩니다.
즉 업계 경쟁은 **확인 절차를 줄이는 방향**으로 가고 있고, 그래서 결정적 검증 레이어가 필요합니다.

> **송금·이체는 우리 범위가 아닙니다.** 이 표에 넣은 것은 "자연어 금융 실행이 이미 상용화됐다"는
> 사실 확인용입니다. 우리 MVP는 **증권 주문 파싱**만 다룹니다.

## 2. 확인·착오방지 (국내 규범과 증권사 가드) — 우리의 가장 아픈 반론

가장 먼저 나올 질문은 **"그냥 확인 화면 띄우면 되는 거 아닌가요?"** 입니다. 근거가 실제로 있습니다.

| 대상 | 실제 내용 | 한계 (원문 근거) |
|---|---|---|
| [한국투자증권 kis-ai-extensions](https://github.com/koreainvestment/kis-ai-extensions) — 증권사 **공식** | `kis-prod-guard` 훅이 실전 모드 주문을 차단하고 "종목/수량/금액을 사용자에게 명시하고 확인받으라"고 출력 | ① 게이트가 **Bash 명령 문자열에 `/api/orders`가 있는지 grep 1회** — MCP 호출·스크립트 실행·변수 조립 URL은 통과 ② 훅이 무상태라 확인 여부를 알 수 없어 prod 주문을 **매번 차단** ③ README 자백: "Cursor는 도구 호출 전 가로채기를 지원하지 않으므로 안전장치는 규칙 파일로 **대체**됩니다" |
| [토스증권 주문 API](https://developers.tossinvest.com/docs/order) | `confirmHighValueOrder` = "착오주문 방지 플래그", 1억원 이상 주문에 `true`가 아니면 400 | ① 임계가 **1억원 하나** — 미만 주문엔 아무 작동 없음 ② required가 아닌 **요청 본문 boolean**이라 LLM이 400을 받고 스스로 `true`로 채워 재시도 가능 ③ 요청 스키마에 **사용자 원문을 담는 필드가 없어** 뒤집힘을 원리적으로 판별 불가 |
| [금융투자협회 「주문착오방지 모범규준」](https://law.kofia.or.kr/service/law/lawFullScreenContent.do?seq=232&historySeq=615) | 20억 초과 경고 / 50억 초과 보류. "매수화면은 붉은색 + 타원형" 등 화면 규범 | **금액·수량 임계 + 사람 눈** 설계. 우리 MVP는 이 규준을 대체하지 않고 **그 앞단**에 놓입니다 |
| [tossinvest-cli](https://github.com/JungHoonGhae/tossinvest-cli) / [tossinvest-mcp](https://github.com/scjang01/tossinvest-mcp) | preview→`--confirm <token>` 바인딩, 한도·킬스위치 | 파라미터↔파라미터 일치. **원문 발화는 입력이 아님** |

### 우리 답변 (검증된 사실만)

1. **echo-back은 사용자가 자기 발화를 기억한다고 가정합니다.** 매수↔매도, 이하↔이상은
   사람이 확인 화면에서 가장 잘 놓치는 유형입니다. 우리는 사람이 아니라 **원문 텍스트**를 기준으로 대조합니다.
2. **kis-ai-extensions는 (d)를 검증이 아니라 회피로 처리했습니다.** `kis-order-executor/SKILL.md` 원문:
   "**'삼성전자 매수해줘'처럼 직접 주문 요청이 아니라**, 종목 선택 → 전략 실행 → 신호 확인을 거친 뒤에만 주문이 발생한다."
   BUY/SELL은 전략엔진의 `SignalResult`에서 나옵니다. 그런데 같은 저장소 `package.json`은
   "order execution **via natural language**"라고 광고합니다 — 자연어 주문 UX를 내세우면서 정작 주문 방향은 자연어에서 뽑지 않습니다.
3. **같은 문서에 우리가 잡는 축이 산문으로만 적혀 있습니다.** SKILL.md: "매수 지정가는 현재가 **이하**, 매도 지정가는 현재가 **이상**".
   LLM에게 주는 지시문일 뿐 이를 검사하는 코드가 없습니다.

## 4. 의도-행동 의미 일치 검증 — **직접 경쟁 (18건)**

여기가 진짜 선행연구입니다. **우리는 이 문제를 처음 제기한 팀이 아닙니다.**

| 대상 | 접근 | 우리와의 차이 |
|---|---|---|
| [PV-SQL](https://arxiv.org/html/2604.17653v1) | 질문에서 키워드 패턴으로 제약 추출 → SQL이 해당 구문을 포함하는지 **결정적** 대조 ("unique"→DISTINCT, "how many"→COUNT) | **방법론적 쌍둥이.** 다르게: 도메인이 SQL(재실행 가능)이고 우리는 **비가역 금융 주문**, 언어가 영어, 실행 권한 개념 없음 |
| [GBV-SQL](https://arxiv.org/abs/2509.12612) | 생성된 SQL을 자연어로 **되번역**해 원 질문과 정합성 검증 | LLM 되번역 기반 = 확률적. 우리는 정규식 규칙 = 결정적·감사 가능 |
| [InferAct](https://arxiv.org/abs/2407.11843) | 실행 전 툴 호출을 가로채 Theory-of-Mind로 의도 역추론 → 원 지시와 대조 | **문제 정의가 우리와 동일.** LLM 추론 기반이라 판정 근거가 재현되지 않음 |
| [The Task Shield](https://arxiv.org/abs/2412.16682) (ACL 2025) | 모든 지시·툴 호출이 사용자 목표에 기여하는지 검증. AgentDojo ASR 2.07% | 프레이밍이 "유해 차단"이 아닌 "의도 정렬"로 우리와 같음 |
| [ProvenanceGuard](https://arxiv.org/abs/2607.01236) | 툴 호출의 각 **인자가 컨텍스트 내 추적 가능한 근거로 뒷받침되는지** 판정 → 아니면 차단 | **우리 프로버넌스 레이어의 최근접 선행연구.** 근거 범위가 '에이전트 컨텍스트'인 반면 우리는 '**사용자 발화 원문**'으로 좁힘 |
| [SPARC](https://arxiv.org/pdf/2603.15473) (IBM, CAIS '26) | syntactic(규칙) + semantic + transformation 3중 검증 | 규칙 기반 앞단이 있다는 점에서 유사, 도메인 무관 툴콜 |
| [DidYouMean](https://arxiv.org/abs/2303.16857) (EMNLP 2023) | 캘리브레이션 신뢰도로 고확신 실행 / 저확신 되묻기 | **"보류할까 실행할까" 트레이드오프를 선점한 논문.** 우리 보류율 논의는 이 위에 서 있음 |
| [DialSQL](https://aclanthology.org/P18-1124/) / [MISP](https://arxiv.org/pdf/1910.05389) | 오류 구간 식별 → 객관식 되묻기 | 되묻기 축 선행. 우리는 되묻지 않고 **보류**로 처리 |
| [Galileo Tool Selection Quality](https://docs.galileo.ai/concepts/metrics/agentic/tool-selection-quality) | "올바른 도구와 **올바른 인자**를 골랐는가" 3차원 평가 | **문장 수준에서 우리와 동일.** 다만 이것은 사후 **평가 지표**이지 실행 차단 게이트가 아님 |

## 6. 그래서 우리가 남긴 자리 (과장 없이)

**우리가 처음 한 것이 아닌 것** — 정직하게 인정합니다.
- 실행 직전 게이트 (US8635296B2, 1999년대 계열 / kis-prod-guard / Robinhood)
- 의도-행동 의미 대조 (InferAct, Task Shield, GBV-SQL, KR20260047202A)
- 규칙 기반 결정적 대조 (PV-SQL)
- 인자별 근거 추적 (ProvenanceGuard)
- 보류 vs 실행 트레이드오프 (DidYouMean)

**교집합이 비어 있는 지점** — 이 5개를 **동시에** 만족하는 공개 사례를 찾지 못했습니다.

1. **한국어** 발화 원문 기준
2. **증권 주문**(비가역·금전) 도메인
3. **결정적 규칙** (LLM 재호출 없음 → 판정 근거를 로그로 제시 가능, 같은 입력에 같은 출력)
4. **필드별 실행 권한** — 값이 사용자 발화에 근거하는지를 필드 단위로 판정하고,
   근거 없는 필드는 `MODEL_INFERRED`로 표시해 실행 권한을 주지 않음
5. **재현 가능한 측정** — 공개 코퍼스(189건 자체 + AgentDojo 한국어 72 + BFCL 무관질의 30)와
   pass^k 재현성, Python↔TS 512건 패리티 픽스처

가장 가까운 단일 선행연구는 **PV-SQL**(방법론)과 **ProvenanceGuard**(권한 개념)이며,
둘 다 한국어도 금융 주문도 아닙니다.

## 7. 예상 질문과 답변 (심사용)

**Q. Zenity/Operant가 이미 실행 전 의도 검증을 한다는데요?**
A. 대조 기준이 다릅니다. 그쪽은 *조직 정책 ↔ 액션*, 우리는 *이 사용자가 방금 한 말 ↔ 이 주문서*입니다.
정책상 '매도'가 허용된 액션이면 매수→매도 뒤집힘은 그쪽 정의상 정상 통과합니다.

**Q. 그냥 확인 화면 띄우면 되지 않나요? 한투도 토스도 그렇게 합니다.**
A. 맞습니다. 그리고 그것이 현재 업계 표준입니다. 다만 ① 사람은 매수/매도·이하/이상을 화면에서 잘 놓치고
② 업계는 확인 절차를 **줄이는** 방향으로 가고 있으며(신한 슈퍼SOL 사례)
③ 한투 훅은 `/api/orders` grep 하나에 의존하고 Cursor에서는 프롬프트 규칙으로 열화된다고 스스로 문서에 적어뒀습니다.
우리는 확인 화면을 없애자는 게 아니라, 확인 화면에 **무엇을 강조해 띄울지**를 결정적으로 계산합니다.

**Q. 토스에 이미 착오주문 방지 플래그가 있는데요?**
A. `confirmHighValueOrder`는 1억원 임계 하나이고, LLM이 스스로 `true`로 채워 보낼 수 있는 요청 본문 필드입니다.
무엇보다 그 API 요청 스키마에는 사용자 원문을 담는 필드가 없어, 뒤집힘을 판별할 입력 자체가 없습니다.

**Q. 최초인가요?**
A. 아닙니다. (d) 축에는 최소 18건의 직접 선행이 있고 특허도 3건 겹칩니다.
우리 기여는 이 문제를 **한국어 증권 주문에서 결정적 규칙 + 필드별 실행 권한으로 구현하고 재현 가능하게 측정한 것**입니다.
