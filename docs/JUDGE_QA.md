# 심사 예상 질문 20문항 (적대적)

호의적인 질문은 넣지 않았습니다. **답변은 저장소의 실제 결과로만** 하고,
방어가 안 되는 것은 "현재 답이 없다"고 적었습니다. 근거는 `docs/JUDGE_EVIDENCE.md` 대조표 참조.

**답변 3원칙**
1. "0%"를 단독으로 말하지 않는다 — 항상 `0 / 142` 처럼 **n 을 붙인다**.
2. 하네스 결함 5건을 **먼저** 꺼낸다 — 먼저 말하면 운영 루프의 증거, 지적당하면 허술함의 증거가 된다.
3. 모르는 것은 모른다고 한다. 이 프로젝트의 유일한 진짜 방어선은 정직성이다.

---

## A. 문제 정의 · 필요성

**Q1. MTS에 이미 조건주문·스탑로스 UI가 있는데 왜 자연어입니까?**
전제가 다릅니다. 조건주문 UI를 없애자는 게 아니라 **그 딸깍을 대신 하자**는 겁니다. 지금은 메뉴를 찾아 들어가 조건 유형을 고르고 기준가·수량을 넣는 딸깍이 열 번이라, 정작 필요한 손절을 안 걸고 넘어갑니다. 말로 하면 시스템이 눌러주되 **무엇을 주문할지는 100% 사용자가 정합니다.** 그리고 이미 현실입니다 — **토스증권이 2026-08-13 오픈API 를 정식 출시**하며 LLM 연동 주문을 공식 안내했습니다. 다올투자증권은 대화형 'MCP 트레이딩'을 2026-07-27 사전예약 개시(8월 출시 예정), 한국투자증권은 공식 GitHub 로 AI 에이전트 확장과 **실전 주문 전 사용자 승인 강제**를 제공합니다(형태는 서로 다릅니다). 질문은 "할 것인가"가 아니라 **"안전하게 할 것인가"** 입니다.

**Q2. 그래서 이게 편의 기능 아닙니까?**
아닙니다. GUI 에서는 매수가 붉은 타원, 매도가 푸른 사각형으로 **눈에 보이게** 분리됩니다 — 금융투자협회 「금융사고 방지 모범규준」 제2-22조가 요구하는 안전장치입니다. 음성·대화 채널에는 그 화면이 없습니다. 우리 하네스는 **사라진 시각적 안전장치를 대체하는 계층**입니다.

**Q3. 왜 한국어에서 특히 필요합니까?**
한국어는 방향·조건이 **어미와 조사에 실립니다**("사지 마" vs "사지 말고 팔아", "이하" vs "이상", "밑돌지 않으면"). 한 음절 차이가 정반대 의미가 되고 어순도 자유롭습니다. 실제로 외부 데이터셋(BULL) 분석에서 임계 표현이 94:1로 편중돼 있었고, 그 희귀 대역에서 모델이 100% 실패했습니다(`BULL_KO_BENCHMARK.md`).

**Q4. 음성 인식 자체가 틀리면 어떻게 합니까?**
**정직하게 말씀드리면 이건 우리가 못 막습니다.** ASR 이 "삼성전자"를 "삼송전자"로 들으면 하네스는 그 텍스트를 기준으로 판단합니다. 다만 종목명이 사전에 없으면 **보류로 떨어져** 잘못된 주문이 나가지는 않습니다. 코퍼스에 ASR 잡음 스타일 18건이 있으나 **현실적 오류 패턴 반영은 부족하며, 알려진 공백입니다.**

**Q4-1. AI가 알아서 주문을 내는 건 투자일임업 아닙니까? 등록 없이 가능합니까?**
사용자가 **종목·수량·가격·시기를 전부 지정**하면 투자일임이 아니라는 금융위·금감원 **법령해석**(2015.6.17)이 있습니다 — 법 조문이 아니라 **유권해석**입니다. 그래서 하네스에 **위임 거부 규칙**(`DELEGATION`)을 넣었습니다: "적당히"·"알아서"·"나눠서"·"눈치껏"·"좋은 가격에" 는 **수량이 채워져 있어도** `delegation→abstain` 으로 보류합니다(`test_delegation_refused` 로 고정). 안전 기능이자 준법 리스크를 줄이기 위한 보수적 설계입니다. **다만 실제 상용화에는 별도 준법·법률 검토가 필요합니다** — 저희가 법률 자문을 받은 것은 아닙니다.

## B. 기술적 타당성

**Q5. LLM 성능을 높이면 해결되는 것 아닙니까?**
실험1에서 프론티어 천장인 **Opus 5 도 47건 중 3건**을 틀렸습니다. 4bit 실측에서는 크기 곡선이 **단조롭지도 않았습니다** — 8B(8.0%) = 32B(8.0%) < 14B(13.6%). 크기로는 예측조차 안 됩니다.

**Q6. 그럼 LLM 을 빼고 규칙만으로 만들면 되지 않나요?**
규칙만으로는 표현 다양성을 못 덮습니다("던지삼", "손 떼자", 방언·오타). LLM 은 **커버리지**를, 하네스는 **방향·조건의 확정성**을 담당하는 역할 분담입니다. 실제로 하네스 L3 단독으로 raw 오류 6건을 6/6 복원했지만, 그건 L3 가 아는 표현이었기 때문입니다.

**Q7. 하네스도 결국 정규식 아닙니까? 우회하면 끝 아닌가요?**
맞습니다, 정규식이 핵심입니다. 그래서 **우회를 실제로 시도했습니다** — 규칙 전문을 공격자에게 공개한 적응형 라운드에서 v2.1 이 **18% 뚫렸습니다.** 다수의 미등재·불확실 표현은 **보류로 떨어집니다**(fail-closed). **다만 목록 밖 표현 전체를 보장하지는 않습니다** — 근거 인용(evidence-grounding) 통로에 잔여 위험이 남아 있어, 인젝션이 없는 발화에서 모델이 `각이다`·`ㄱㄱ` 같은 **무방향어를 근거로 제시하면 통과할 수 있습니다**(`smoke/RESULTS.md` §12 한계). 인젝션이 있는 경우는 구조적으로 차단했지만, 이 대역은 열려 있습니다.

**Q8. 왜 확률적 모델(가드 모델) 대신 규칙입니까? FinGuard 같은 게 있는데요.**
과제가 다릅니다. FinGuard(arXiv:2605.29427)는 **규제 위반 탐지**, Qwen3Guard 는 **유해성 분류**입니다. 어느 쪽도 "주문 필드가 사용자 발화와 일치하는가"를 보지 않습니다. 그리고 모범규준 제2-18조가 주문 검증 시스템에 **"적정성을 검증할 수 있는 기준과 절차"** 를 요구하는데, 확률적 출력은 이를 충족하기 어렵습니다.

**Q9. 기존 guardrail 제품(NeMo Guardrails 등)과 뭐가 다릅니까?**
기성 output rail 은 **스키마 유효성·유해성·환각**을 봅니다. 그런데 `{"side":"SELL","condition":"GE"}` 는 **완벽하게 유효한 JSON 이고 유해어도 없습니다.** 사용자가 "매수"·"이하"라고 말했다는 사실과 대조해야만 오류인데, 그 대조는 기성 도구가 하지 않습니다.

**Q10. 결정적 금융 가드레일은 이미 논문이 있습니다(Lean 4 정리증명).**
arXiv:2604.01483 말씀이시면, 그 논문은 **이미 구조화된 주문의 정책 준수**(한도 초과 등)를 증명합니다 — 자연어 파싱의 방향 역전은 **명시적으로 범위 밖**이고, **평가 데이터·수치가 없는 preprint** 입니다. 저희는 파싱 자체를 보고 720건 실측이 있습니다. **한도를 아무리 잘 지켜도 매수가 매도로 뒤집히면 소용없습니다.**

**Q11. latency 가 늘어나지 않습니까?**
하네스 L3 는 정규식 기반이라 모델 호출 대비 무시할 수준으로 예상되지만 **측정하지 않았습니다.** 다만 raw 와 하네스를 각각 1회 호출하므로 **실서비스에서는 하네스 경로 1회만** 쓰면 됩니다(비교 데모라서 2회 호출).

## C. 평가 신뢰성

**Q12. 공격도 정답도 채점도 본인이 했는데 0%를 어떻게 믿습니까?**
**가장 아픈 지적이고, 전적으로 인정합니다.** 코퍼스 720건 전부 자체 생성이고, 핵심 189건 중 제3자 판정은 12건(6%)뿐이며 **사람 라벨은 0건**입니다. 완화책은 **저자가 통제하지 않은 분포 축 3개**(BULL·AgentDojo·BFCL)이고, 결정적으로 **외부 분포가 들어올 때마다 하네스 결함이 나왔습니다 — 3연속.** 자가생성만으로 부족하다는 걸 저희가 먼저 실증했습니다.

**Q13. 데이터셋이 너무 작지 않습니까?**
작습니다. 공격자당 n=20~22 라 이항 신뢰구간이 넓어(35%일 때 [15%, 59%]) **공격자 간 순위는 통계적으로 구별되지 않습니다** — 탐색적 결과로만 봅니다. 주장의 무게는 풀 집계(n=142)와 결정적 회귀에 싣습니다.

**Q14. "치명오류 0%"가 안전하다는 뜻입니까?**
아닙니다. 정확히는 **"이 평가 세트에서 관측된 치명오류 0건"**(`0 / 142`, 95% 상한 약 2.6%)입니다. 절대 안전이 아닙니다. 실제로 규칙을 아는 공격자는 18%를 뚫었고, 저희도 **하네스 자체 결함 5건**을 찾아 고쳤습니다.

**Q15. adaptive attack 에서 뚫렸는데 안전하다고 할 수 있습니까?**
"안전하다"고 하지 않습니다. 저희 주장은 **"뚫리면 확정 대신 확인 요청으로 패치하는 루프가 제품"** 이라는 것입니다. 3라운드에 걸쳐 13% → 18% → 3% 로 수렴했고, 뚫린 지점은 매번 **"하네스가 확신 없이 덮어쓴 곳"** 이었습니다.

**Q16. temperature 0 인데 왜 숫자가 바뀝니까?**
프로바이더·서빙 비결정성입니다. 그래서 pass³ 로 **측정했습니다** — 88건 중 흔들린 케이스 1건(1.1%). 그리고 raw 는 '한번이라도 치명' 8건 vs '항상 치명' 7건이라 **단일 실행이 1~2건을 과소계상**합니다. 하네스는 3회 전부 안전 88/88.

**Q17. 클라우드 결과와 로컬 4bit 결과를 같이 놓는 건 부당하지 않습니까?**
맞습니다. **순수 정밀도 ablation 이 아닙니다.** 로컬 vLLM 은 guided decoding 으로 스키마가 실제 강제되는 반면 클라우드 소형 Qwen 은 프롬프트 폴백이었습니다. 그래서 **"4bit 가 더 좋다"고 주장하지 않습니다** — CI 도 겹칩니다(Fisher p=0.145).

## D. 제품 · 사업성

**Q18. 40%씩 되묻는 서비스를 누가 씁니까?**
40%는 **확인 규칙을 노려 만든 적대 코퍼스** 수치입니다. 하나의 숫자가 아니라 **입력 분포마다 다릅니다** — 방향이 문자로 분명하면 0.0%(임계 88건), 인젝션이 있어도 발화가 분명하면 0.0%(AgentDojo 72건), 표현이 흐릿해지면 11.7%(일상어체 **합성** 240건), 공격자가 규칙을 알고 노리면 ~40%. 즉 **위험도가 올라갈수록 fail-closed 가 더 적극 개입**합니다. 분모와 코퍼스 성격을 함께 정리한 표는 [`docs/CONFIRMATION_RATE.md`](CONFIRMATION_RATE.md) 에 있습니다.

**정직하게 덧붙이면**: 240건의 11.7%는 낮지 않고(열 번에 한 번 이상), 온프레미스 4bit 에서는 풀정밀 대비 **2.1% → 10.6%** 로 늘어납니다 — 우리가 주장하는 배포 환경이 하필 사용성이 가장 나쁜 조건입니다. 그리고 위 수치는 **전부 합성 코퍼스** 기준이며 실제 사용자 발화로 측정한 적이 없습니다.

**Q19. 오탐으로 좋은 주문을 막으면 누가 책임집니까?**
하네스는 **주문을 취소하지 않습니다** — "이 주문 맞으신가요?"를 한 번 더 물을 뿐이고 사용자가 확인하면 나갑니다. 확정을 막는 게 아니라 한 단계를 추가하는 구조입니다.

**Q20. 금융회사가 이걸 실제 주문 시스템에 넣을 수 있습니까? 자체 개발하면 되지 않나요?**
규칙표도 코퍼스도 베낄 수 있습니다 — **이 저장소는 공개돼 있습니다.** 그래서 해자는 파일이 아닙니다. 못 베끼는 것은 **새로운 실패 → 공격 재현 → fail-closed 방향 패치 → 회귀 테스트 고정 → Python/TS 패리티 검증**으로 이어지는 **safety engineering loop** 입니다. 실제로 이 루프가 하네스 결함 5건과 우회로 4건을 잡아냈고, 회귀는 46 → 56건으로 늘었습니다. 규칙표 한 벌은 스냅샷이지만, 새 공격이 들어올 때마다 안전한 방향으로 수렴시키는 절차는 조직 역량입니다. 도입 유인은 전자금융거래법 제9조 제1항이 거래지시 처리 과정의 사고에 **무과실책임**을 지우고, 시행령 제8조가 이용자 고의·중과실을 4개 유형으로 좁게 한정해 **사후 면책 통로가 좁다**는 점입니다. **단, 오파싱이 제9조의 '사고'에 포섭된다는 판례는 없습니다 — 해석상 주장입니다.**

**Q21. 현재 데모는 실제 주문 API 와 연결되지 않았는데 MVP 라고 할 수 있습니까?**
**연결되어 있지 않습니다.** 모의 시세·모의 체결이며, 이건 **의도된 범위**입니다 — 저희가 검증하려는 것은 체결이 아니라 **"발화 → 주문 파라미터" 변환의 안전성**이고, 그 층은 실제 API 앞단에 그대로 붙습니다. 실거래 연동은 증권사 계약·심사가 선행되어야 합니다.

**Q22. 증권 주문 말고 다른 금융거래로 확장 가능합니까?**
구조적으로는 **되돌릴 수 없는 금융 행위**(이체·대출 실행·보험 해지 등)에 같은 패턴이 적용됩니다 — "사용자가 말한 파라미터 = 시스템이 실행할 파라미터"를 결정적으로 대조하는 층이니까요. **다만 현재 구현·검증된 것은 증권 주문뿐이며**, 다른 도메인은 규칙표를 새로 만들어야 합니다. 확장했다고 주장하지 않습니다.
