# Related Work 초안 — FinSQL/BULL 대비 우리 연구의 위치

> 대상 논문: **FinSQL: Model-Agnostic LLMs-based Text-to-SQL Framework for Financial Analysis**
> Zhang et al., Zhejiang Univ. × Hundsun Technologies, SIGMOD 2024 (arXiv:2401.10506v1)
> 데이터셋: **BULL** (4,966 NL-SQL쌍, 中/英 병렬, fund·stock·macro)

---

## 1. 왜 이 논문이 우리에게 가장 중요한가

**전제가 우리와 동일합니다.** 논문 서론의 핵심 논거:

> "existing state-of-the-art LLMs-based Text-to-SQL methods typically depend on OpenAI's APIs, such as
> GPT-3.5-turbo or GPT-4, which are **expensive and have risks of information leakage**. Therefore, these
> methods **cannot be used in the financial applications where the information privacy is critically important**."

즉 "금융은 프라이버시 때문에 프론티어 API를 못 쓰고 오픈소스 로컬 LLM을 써야 한다"는 우리 프로젝트의 출발점을,
SIGMOD 논문이 Hundsun Technologies(알리페이·초상은행 등 50개+ 금융기관에 납품)의 실제 사업 맥락에서 동일하게 주장합니다.
**→ 우리 전제를 인용 한 줄로 방어할 수 있는 최상급 근거.**

또한 이 논문은 **로컬 모델이 프론티어를 이길 수 있음**을 보여줍니다:

| 방법 | EX(정확도) | SQL당 비용 |
|---|---|---|
| **FinSQL + LLaMA2-13B (로컬)** | **82.2%** | — |
| DAIL-SQL + GPT-4 | 75.0% | $0.1581 |
| DAIL-SQL + ChatGPT | 55.0% | $0.0053 |
| C3 + ChatGPT | 2.0% | $0.0078 |
| RESDSQL* + mT5 | 66.9% | — |

(BULL-cn: Baichuan2 76.6% / mT5 70.4%)

**→ "로컬이라 성능이 부족하다"는 반문에 대한 반박 근거.** 도메인 튜닝된 로컬이 GPT-4 기반 파이프라인을 앞섭니다.

## 2. FinSQL의 구조와 우리 하네스의 대응 관계

FinSQL은 3개 컴포넌트로 구성됩니다.

| FinSQL 컴포넌트 | 내용 | 우리 하네스의 대응 |
|---|---|---|
| ① Prompt Construction | 병렬 schema linking + 하이브리드 데이터 증강(CoT/동의어/skeleton) | **L2 강화 프롬프트 + few-shot** (대응됨) |
| ② PEFT (LoRA plugin hub) | LoRA(<1% 파라미터)로 DB별 플러그인, 병합·교차DB 전이 | 우리는 **미적용** (파인튜닝 없이 추론시 방어) |
| ③ **Output Calibration** | 오타수정 → SQL 키워드 성분 추출 → 구조 호환성으로 후보 클러스터링 → 최대 클러스터 선택(self-consistency) → 최종 보정 | **L3 결정적 검증과 가장 가까움 — 그러나 목적이 다름** |

### ★ 핵심 차이: Output Calibration은 "문법·스키마 유효성"을, 우리 L3는 "의미 방향"을 본다

FinSQL의 calibration이 잡는 오류는 논문 Figure 12에 예시된 3종입니다:
1. **Typo error** — `b on a.personalcode = a.personalcode` 같은 조인 문법 오류
2. **Invalid column** — 존재하지 않는 컬럼(`aquirementrium` ← 정답 `aquireramount`)
3. **Table–column mismatch** — 컬럼이 잘못된 테이블에 귀속

**전부 "실행이 되는가"의 문제이지 "의도한 방향인가"의 문제가 아닙니다.**
`totalshares > 10000000000`을 `<`로 뒤집어도 SQL은 문법적으로 완벽하고 스키마도 유효하며 실행도 됩니다 —
FinSQL의 calibration은 이걸 **원리적으로 잡지 못합니다.**

우리 L3는 정확히 그 지점을 겨냥합니다: 방향(매수/매도·이하/이상)을 모델 추론이 아니라
**사용자 발화의 문자 그대로**에서 결정적으로 강제합니다.

### ★ 정량 대조: calibration의 기여도

논문 ablation (BULL-cn / BULL-en):

| 제거 항목 | EX 하락 |
|---|---|
| w/o Output Calibration | **-1.3 / -1.5 %p** |
| w/o Self-Consistency | -0.2 / -0.3 %p |
| w/o Alignment | -1.1 / -1.2 %p |
| w/o Augmented Data | -3.8 / -4.7 %p |

**Output Calibration 전체가 약 1.5%p 기여**에 그칩니다(데이터 증강의 1/3 수준).
반면 우리 하네스는 **적대적 입력 하 치명오류를 21.1% → 0/142(하네스 v2, 95% 상한 2.6%)** 로 낮춥니다.
(초기 v1 은 8B 를 21.1→11.3 으로 낮췄으나 32B 는 9.2→11.3 으로 **악화**시켰고, 그 하네스 유발 오류를 없앤 v2 가 정본입니다.)

> ⚠️ **정직한 단서**: 두 수치는 같은 축이 아닙니다. FinSQL은 *정상 데이터에서의 전체 실행정확도(EX)*를,
> 우리는 *적대적 입력에서의 방향 오류율(ASR)*을 잽니다. 직접 비교가 아니라
> **"무엇을 표적으로 삼았는가"의 차이**로 서술해야 합니다. 같은 표에 나란히 놓으면 안 됩니다.

## 3. FinSQL이 다루지 않는 것 = 우리의 빈칸

논문 전문(17쪽)을 검색한 결과:

| 용어 | 등장 횟수 |
|---|---|
| adversarial / attack / injection | **0** |
| safety / security | **0** |
| privacy / leakage | 4 (전부 *동기* 서술 — "그래서 로컬을 쓴다") |

**프라이버시를 이유로 로컬 모델을 채택했으면서, 그 로컬 모델이 적대적 입력에 얼마나 취약한지는 전혀 측정하지 않았습니다.**
이것이 우리 연구의 정확한 위치입니다:

> FinSQL은 "로컬 LLM으로도 금융 text-to-SQL을 잘할 수 있다"를 보였다.
> 우리는 "그 로컬 LLM이 적대적 입력에서 **방향을 뒤집는다**"를 보이고, 그것을 막는 검증층을 제안한다.

## 4. BULL 데이터셋 자체 분석에서 나온 근거 (우리가 직접 측정)

BULL 4,966쌍을 직접 분석해 얻은 결과 — 논문에 없는 수치입니다.

### (1) 방향성 비교 연산자의 심각한 불균형
전체의 **26.0%(1,291건)**가 방향성 비교(`<`,`>`,`<=`,`>=`)를 포함하는데:

```
>  1116건 (86.4%)      <   208건 (16.1%)
>=   84건 ( 6.5%)      <=   12건 ( 0.9%)
```

`>`가 `<`의 **5.4배**, `>=`가 `<=`의 **7배**. **"이하(`<=`)"는 사실상 부재(12건)**입니다.
→ 이 데이터로 학습·평가하면 모델이 "초과" 쪽으로 편향되고, 우리가 관측한 임계 방향 오류와 정확히 맞물립니다.
→ 우리 한국어 코퍼스는 **LE/GE를 의도적으로 균형**있게 설계해야 한다는 근거.

### (2) 전문가 라벨에도 방향 노이즈가 존재
명확한 중국어 방향어 + 단일 조건 788건을 검사:

| 구분 | 비율 |
|---|---|
| 일치 | 96.6% |
| **경계 차이** (예: 以上(≥)인데 `>` 사용) | **2.8%** |
| **방향 완전 반전** (예: 超过(초과)인데 `<`) | **0.6%** |

금융 전문가·데이터 사이언티스트가 라벨링한 SIGMOD 논문 데이터셋조차 **임계 방향에서 3.4%가 어긋납니다.**
→ GBV-SQL(arXiv:2509.12612)이 지적한 "Gold Errors"와 같은 현상.
→ **"이하/이상 방향은 사람도 기계도 틀리는 고위험 지점"**이라는 우리 주장의 외부 증거이자,
   BULL을 gold로 재사용할 때의 주의사항.

### (3) BULL은 전부 읽기 전용 — 주문(상태 변경)은 없음

```
SQL 구문 종류(4,966건):  select 4,966 / 그 외 0
주문 실행 스키마(BUY·SELL·주문유형·주문수량):  없음
```

78테이블·1,167컬럼을 전수 조사했으나 매매 주문 스키마는 존재하지 않습니다
(`lc_buyback`은 기업 자사주 매입 *공시*이지 주문이 아님).
→ **text-to-SQL은 조회, 우리는 되돌릴 수 없는 상태 변경.** 실행 오라클로 검증할 수 없다는
   구조적 차이가 데이터로 확증됩니다.

## 5. 서술 문단 초안 (기획서/논문용)

> 금융 도메인의 자연어-구조화 질의 변환은 FinSQL[Zhang et al., SIGMOD 2024]이 대표적이다.
> 이 연구는 GPT-4 API의 비용과 **정보유출 위험** 때문에 금융 현장에서는 오픈소스 LLM을 로컬로
> 운용해야 한다고 지적하고, LoRA 기반 경량 튜닝과 출력 보정(output calibration)을 결합해
> 로컬 LLaMA2-13B로 EX 82.2%를 달성하여 GPT-4 기반 파이프라인(75.0%)을 앞섰다.
> 본 연구는 이 전제(프라이버시 → 온프레미스 로컬 LLM)를 공유하되, 세 지점에서 갈라진다.
>
> 첫째, **대상이 조회가 아니라 주문이다.** FinSQL이 제안한 BULL 벤치마크는 4,966건 전부가
> SELECT 질의이며, 78개 테이블·1,167개 컬럼 어디에도 매매 주문(BUY/SELL) 스키마가 없다.
> 조회는 틀리면 다시 실행하면 되지만, 주문은 되돌릴 수 없다. 국내 거래소 착오매매 구제도
> 시장가격과 크게 차이나는 **가격 이탈**을 대상으로 하지, 방향(매수↔매도) 착오 자체는 구제 사유가 아니다.
>
> 둘째, **검증의 표적이 다르다.** FinSQL의 output calibration은 오타·존재하지 않는 컬럼·
> 테이블-컬럼 불일치 등 *실행 가능성*을 보정하며, ablation 기준 약 1.5%p를 기여한다.
> 그러나 `>`를 `<`로 뒤집은 질의는 문법적으로 유효하고 스키마도 정상이므로 이 계열의 보정으로는
> 원리적으로 검출되지 않는다. 본 연구는 방향(매수/매도, 이하/이상)을 모델 추론이 아니라
> 발화의 표층 단서에서 결정적으로 강제하는 검증층을 제안한다.
>
> 셋째, **적대적 조건을 다룬다.** FinSQL 전문에는 adversarial·attack·injection·safety가
> 한 번도 등장하지 않는다. 프라이버시를 이유로 로컬 모델을 택했으면서 그 모델의 적대적 취약성은
> 측정되지 않은 것이다. 본 연구는 프론티어 모델이 생성한 공격 하에서 로컬 Qwen의 방향 오류율을
> 측정하고(8B 평균 26%), 제안하는 검증층이 이를 12%로 낮춤을 보인다.
>
> 부가적으로, BULL 자체 분석에서 방향성 비교 1,291건 중 `>`:`<`가 5.4:1, `>=`:`<=`가 7:1로
> 편중되어 있으며, 명확한 방향어를 포함한 단일조건 788건 중 3.4%에서 자연어 표현과 SQL 연산자가
> 어긋남을 확인했다. 이는 임계 방향이 전문가 주석 환경에서도 오류가 발생하는 고위험 지점임을 시사한다.
